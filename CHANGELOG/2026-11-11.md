# CHANGELOG - 2026-11-12

## Target
`solvitaire_installv5.3.3.exe` (37,803,696 bytes, SHA-256: `35650a706fa713f0cb9f1153759bc077ac490044b30e7584c10a11e36b28f4b0`)

## Summary
Reverse-engineered a Windows Solitaire installer. It is **not a native game** — it is an InstallForge native PE32 stub bundling two 7-Zip archives, the inner one containing a Launch4j-wrapped Java application with a bundled JRE 1.8.0. Full Java source was recovered via CFR decompilation.

## Key findings

### Installer binary (solvitaire_installv5.3.3.exe)
- Format: PE32 executable, x86 (machine 0x014c), entry `0x10a943`
- Not Go, not Rust, not .NET (no build-info, no .dep-v0, no CLI data directory)
- Section table is zeroed (packed/protected stub); all 6 sections have SizeOfRawData=0, PointerToRawData=0
- PE resources: 4 icons (64x64, 48x48, 32x32, 16x16), version resource, dialog resource, icon group
- Custom resource `SETUPCONFIGURATION` at file offset `1371408` = genuine 7-Zip archive (4,197 bytes)
- Second 7-Zip archive at file offset `1409045` (~36 MB compressed)
- ZIP local header `PK 03 04` at offset `938553` (no EOCD found — not cleanly carveable)
- Embedded PE/x86 stubs (`PE\0\0` + `55 8b ec` prologue) at offsets `511493`, `805399`, `1089072`
- Build strings: libarchive, zlib 1.2.12, libjpeg, Windows APIs (cmd.exe, UninstallFileEntry, UninstallRegistryValue, RtlGetVersion, GetVersionExW, etc.)
- No "solitaire", product name, company name, or version branding anywhere in the binary

### Archive 1 (offset 1371408)
- 11 installer data files: SC.dat, Desktop.dat, Startmenu.dat, OS.dat, default.ifl, licence.rtf, languages.dat, Registry.dat, Commands.dat, Estektop.dat, Variables.dat

### Archive 2 (offset 1409045)
- 171 files including:
  - `solvitaire.exe` — Launch4j wrapper (7,783,773 bytes, 32-bit PE)
  - `solvitairec.exe`, `test3d.exe`, `Uninstall.exe`
  - `solvjre/` — bundled JRE 1.8.0 (java.exe, javaw.exe, keytool.exe, awt.dll, jvm.dll, etc.)
  - `com_solvitaire_app_winuser32.dll` — native JNI library
  - `api-ms-win-core-*.dll` Windows API shim DLLs

### Game launcher (solvitaire.exe → extracted as solvitaire_game.exe)
- Format: PE32 x86, entry `0x00401590`, SizeOfImage `0x001c6000`
- Launch4j Java wrapper; reads config from PE RT_STRING resources (type 0xa)
- JAR embedded as PE overlay at offset `0x001b75fc` (5,984,097 bytes)
- Extracted to `solvitaire_game_from_pe.jar`: Main-Class `com.solvitaire.app.Main`, Class-Path `.`, 1,306 entries
- Dependency: XChart 3.8.1 (`org.knowm.xchart`)
- Class names obfuscated (single letters: `V`, `qn`, `pG`, `iv`, etc.)
- Native library `com_solvitaire_app_winuser32.dll` loaded via JNI (WinUser32 class)

### Decompilation results

**Ghidra 12.1.4 headless** (required JDK 25 — JDK 21 and Ghidra 12.2 were rejected by REA version checks):
- Installer: 2,826 functions → `decompiled_installer/` (C-like pseudocode)
- Game launcher: 240 functions → `decompiled_game/` (C-like pseudocode)
- Ghidra projects: `ghidra_proj_installer/SolitaireInstallerProj`, `ghidra_proj_game/SolitaireGameProj`

**CFR 0.152 Java decompiler**:
- 1,216 `.java` files → `java_source/`
- Key files: `Main.java`, `CommandLine.java` (API command interface), `WinUser32.java` (JNI native declarations)

### Running the game

- `javaw.exe` (from bundled JRE)
- `solvitaire_game_from_pe.jar`
- `com_solvitaire_app_winuser32.dll`

Launch command:
```
cmd /c "C:/sgame/javaw.exe -Djava.library.path=C:/sgame -jar C:/sgame/solvitaire_game_from_pe.jar"
```

API mode (stdin/stdout command interface):
```
cmd /c "C:/sgame/javaw.exe -Djava.library.path=C:/sgame -jar C:/sgame/solvitaire_game_from_pe.jar api"
```
Supported API commands: `reset`, `deal`, `solve`, `step [N]`, `status`, `version <game>`, `difficulty <easy|moderate|hard|seed N>`, `keystroke [modifier] <key>`, `readcards <file>`, `challenge <create|play|boards|stacks|card|cards|score> <n> [folder]`, `mode msft|play`, `skipads`, `list [file]`, `run`, `pause N`, `tracelevel <1-9>`, `exit`.

## Tool configuration notes

- REA (rea-agents 6.7.0) connected; Ghidra provider requires `GHIDRA_INSTALL_DIR` pointing to Ghidra 12.1.x (verified 12.1.4) and `JAVA_HOME` pointing to JDK 25+
- Ghidra 12.2 + JDK 21 were **rejected** by REA version checks; Ghidra 12.1.4 + JDK 25.0.5 work
- REA's MCP transport has a 30s timeout; Ghidra auto-analysis on a 36MB binary takes ~175s, so `analyzeHeadless.bat` was used directly instead of REA's `list_procedures`/`list_strings`/`procedure_pseudo_code`
- `DecompileAll.java` is a compiled GhidraScript (Java API: `DecompiledFunction.getC()`, not removed `getCCode()`; `Function` is in `ghidra.program.model.listing`, not `ghidra.program.model.symbol`)
- Run Ghidra headless with `-import` + `-postScript DecompileAll` (Groovy and Python not supported in this Ghidra build)
- 7-Zip available at `C:\Users\admin\scoop\shims\7z.exe`
